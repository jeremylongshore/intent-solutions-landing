Read-only audit; no forms submitted, no provider queries, no game mission launched. Live HTTP verification and desktop1440/mobile390 Chromium snapshots. Method: webapp-testing skill, sitemap and anchor crawl, deployed local HTML comparison, selected Caddy routing inspection. This is a bounded two-host audit, not a complete estate inventory or user study.

## Priority reachability findings

1. OMA parent information scent is too narrow: company header calls it Omarchy; OMA H1 is “Omarchy plugins. Built in public.” A parent looking for a typing game or visitor seeking a migration kit must know to enter a desktop-plugin portfolio. The games/products are reachable but not recognizable from the company front door.
2. Mobile OMA hides its desktop The Beacon Wakes local-nav shortcut. The first Play The Beacon Wakes CTA is about2049px down the document at390×900; primary and fixedmobile Browse plugins jump beyond the game feature. Desktop gameCTA is around1906px down. The game landing/parentguide is not directly linked from the OMA hub: hub Play goes straight to /play/. The desktop The Beacon Wakes header shortcut is an in-page anchor. The parent guide is reachable via game UI, but whole-game learning path should be discoverable before launch.
3. Perception is not a top-level OMA offering card/navitem. It is an Open Perception link within Listening Post's plugin card, about10056px down on mobile and5212px desktop. It has a distinct public productpage, but no visible company/hub directory return link after client rendering: its Intent Solutions/Perception logo returns to itself. Browser showed customer-access/sign-in actions and GitHub/support/legal; no purchase or crossportfolio discovery link. Do not treat the CTA as proof of ready public purchase.
4. Demos /kobiton/ is live200 and in sitemap but not linked from the catalog or bounded anchor graph. /built-with-claude-code/ is live200 and absent both sitemap/catalog. Decide explicitly whether these belong in curated evidence, archive, or retirement; do not silently call them current flagship products.
5. Deep demo pages often lack a direct company/demo-hub return path. Examples: DiagnosticPro architecture, auction lot architecture, Document Filing Standard, ICO architecture, Learning Platform review and its decision pages, real-estate historical concepts. Some have within-project navigation but not an obvious way to browse the rest of Intent. This matters to visitors landing from search or shared deep URLs.
6. The demo XML sitemap lists top-level offerings but omits44 reachable HTMLsubpages; many are supporting architecture/decision/design variants rather than new offerings. A complete maintained route registry should distinguish offerings from their detail pages, aliases, utilitypages and obsolete artifacts. Do not make a flat100-card directory.
7. Public source naming can mislead: /diagnosticpro-1/ is actually Auction lot intelligence, while /diagnosticpro-2/ is DiagnosticPro architecture. A future canonical route change should preserve redirects and update labels.

## Deliverable implications

The directory needs separate named cards for Beacon, BLUE GOLD BLUE, Perception, Intent Outreach and curated demo offerings, with audience/use/status and direct detail/action. Add topic intent (play/learn, migrate computer, monitor signals, research property) so visitors need not know internal brands. Keep plugin catalog and detailed architecture collections as secondary layers. Require “Explore all Intent” return path on standalone landing pages and common discovery metadata for every public route. Count unique offerings separately from route total.
